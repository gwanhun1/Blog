주문 관리 화면에서 배송 상태를 바꿨다. 상세 화면에는 ‘배송 완료’라고 나오는데, 목록으로 돌아가면 여전히 ‘배송 중’이다. 새로고침하면 맞아진다. 이번에는 주문을 선택하고 뒤로 가기를 눌렀더니 검색 필터가 사라졌다. 다시 상세 화면에 들어갔더니, 방금 작성한 배송 메모도 없다.

겉으로 보면 모두 상태 관리 문제다. 하지만 세 문제를 전역 스토어 하나로 해결하려고 하면, 목록과 상세의 데이터가 왜 달라졌는지, 뒤로 가기가 무엇을 복원해야 하는지, 저장하지 않은 초안을 언제 버려야 하는지가 한곳에 뒤섞인다.

이 글에서는 주문 관리 화면 하나를 놓고 React의 기본 상태부터 Zustand, Redux Toolkit, Jotai, MobX, TanStack Query, 폼과 URL 상태까지 비교한다. 라이브러리 순위를 매기기보다 **같은 화면에서 각 도구를 어디까지 쓰면 일이 줄고, 어디서부터 오히려 일이 늘어나는지**를 살펴보려 한다.

## 주문 화면을 열고, 상태보다 원본을 찾는다

먼저 화면에 있는 값을 나열해 보자. 주문 목록, 검색어, 페이지 번호, 선택한 주문, 배송 메모 초안, 저장 오류, 사이드바 열림 여부. 전부 JavaScript 변수로 표현할 수 있지만, 전부 같은 방식으로 저장할 이유는 없다.

| 화면에 보이는 값 | 둘 곳 | 그 이유 |
|---|---|---|
| 확정한 검색어·필터·정렬·페이지 | URL | 공유, 새로고침, 뒤로 가기에서 같은 조회 조건을 복원해야 한다. |
| 주문 목록·상세·서버가 계산한 합계 | 라우트 데이터 또는 서버 데이터 캐시 | 다른 사용자나 서버 처리에 의해 값이 바뀔 수 있다. |
| 입력 중인 메모·필드 오류 | 폼 상태 | 아직 저장되지 않은 사용자 입력이다. 서버 값과 달라도 정상이다. |
| 현재 화면의 모달 열림 여부 | 해당 화면의 로컬 상태 | 화면을 떠날 때 사라지는 편이 자연스럽다. |
| 여러 화면에서 유지되는 작업 패널 | 공유 스토어 후보 | 라우트를 벗어나도 유지해야 하고, 여러 곳에서 읽고 쓴다. |
| 선택된 주문 수, 필터 조건 표시문 | 원본에서 계산 | 따로 저장하면 원본을 바꿀 때마다 함께 맞춰야 한다. |

![exec-149c9e6d-a4da-4810-b0fc-5c181e002d3f.png](https://res.cloudinary.com/dcfqahfbr/image/upload/v1795240619/cvlog/posts/k6aetwevm5lw4xsrilig.png)


이 표에서 가장 실용적인 질문은 **“이 값이 틀렸을 때, 어디를 보고 맞는 값을 알아낼 수 있는가?”**다. URL과 스토어의 필터가 다를 때 둘 중 하나를 고를 수 없다면, 같은 사실을 두 군데에 저장해 둔 것이다. 주문 상세의 상태가 캐시와 다를 때 서버에 확인해야 한다면, 브라우저에 있는 것은 원본이 아니라 복사본이다.

예외도 있다. 폼 초안은 서버 값의 단순 복제처럼 보이지만, 사용자가 고치는 순간 서버의 *마지막 저장본*과 *저장하려는 다음 값*이라는 서로 다른 사실이 된다. 두 값을 갖는 것이 문제가 아니라, 둘의 역할을 명시하지 않는 것이 문제다. [React의 상태 구조 설계 원칙](https://react.dev/learn/choosing-the-state-structure)

## 검색창 하나에도 서로 다른 세 가지 상태가 있다

주문 검색창에 `홍길동`을 입력한다고 하자. 입력창에는 `홍`, `홍길`, `홍길동`이 차례로 나타난다. 그렇다고 한 글자마다 브라우저 방문 기록에 항목을 추가하고 조회 요청까지 보내야 하는 것은 아니다.

- **입력 중인 문자열**은 로컬에 둔다. 키 입력을 즉시 보여주기 위한 값이다.
- **검색 버튼으로 확정한 조건**은 URL에 넣는다. 다른 사람이 링크를 열었을 때 재현돼야 하는 값이다.
- **그 조건으로 가져온 결과**는 라우트 데이터나 서버 캐시가 관리한다.

여기서 화면을 실제로 느리게 만드는 것은 라이브러리 선택보다 값의 변경 빈도를 구분하지 않는 설계일 수 있다. 입력할 때마다 검색어를 전역에 기록하고, 전역 검색어를 읽는 헤더와 목록과 요약 패널까지 함께 갱신한다면 모든 키 입력에 불필요한 일이 따라붙는다. 반대로 URL에 확정 조건을 기록하지 않으면 뒤로 가기나 링크 공유를 별도로 구현해야 한다.

실시간 검색이 필요하다면 초안 입력은 즉시 갱신하고, 조회 조건만 디바운스할 수 있다. 그때도 히스토리 정책은 따로 결정한다. 타이핑 중 자동 반영에는 `replace`, 명시적인 검색 제출에는 `push`가 자연스러울 수 있다. 단, 모든 화면에서 같은 정책을 쓸 필요는 없다. 중요한 것은 사용자에게 뒤로 가기가 어떤 의미인지 정하는 일이다. React Router에서는 검색 파라미터 변경 자체가 내비게이션이다. [React Router의 `useSearchParams`](https://reactrouter.com/api/hooks/useSearchParams)

검색어를 바꿀 때 페이지를 1로 초기화하는 것도 한 번에 처리하는 편이 좋다. `q`만 URL에 먼저 반영하고 Effect에서 `page`를 바꾸면, 새 검색어와 이전 페이지 번호가 잠깐 조합될 수 있다. 그 조합이 조회 키에 쓰이면 불필요한 요청까지 발생할 수 있다. **하나의 사용자 행동이 바꾸는 값은 같은 업데이트에서 정리한다.**

## Redux Toolkit, Zustand, Jotai, MobX: 같은 ‘전역’이라도 비용이 다르다

URL과 폼, 서버 데이터까지 분리하고 나서도 브라우저 안에서 여러 화면이 공유해야 하는 값이 남을 수 있다. 예를 들어 사용자가 주문 여러 건을 선택해 별도의 작업 패널에 모아두고, 다른 화면으로 이동해도 그 선택을 유지하는 기능이다.

이때부터 공유 상태 도구를 비교하는 것이 의미 있다.

| 방식 | 잘 맞는 경우 | 까다로워지는 지점 |
|---|---|---|
| React `useState` / `useReducer` | 한 화면이나 가까운 컴포넌트가 소유한다. 여러 상태 전이를 한곳에 모으려면 reducer가 유용하다. | 여러 라우트가 독립적으로 같은 상태를 수정하면 끌어올린 상태의 소유 범위가 지나치게 커질 수 있다. |
| React Context + 상태 훅 | 테마·로케일처럼 하위 트리에 값을 전달하거나, 특정 화면에만 상태 범위를 만들기 좋다. | 하나의 Context에 자주 바뀌는 값을 모두 담으면 값이 바뀔 때 이를 읽는 소비자들이 다시 렌더링될 수 있다. |
| [Zustand](https://zustand.docs.pmnd.rs/) | 여러 화면의 작업 패널, 선택 상태처럼 작은 공유 스토어를 빠르게 구성한다. selector로 필요한 조각만 구독할 수 있다. | 액션 이름과 데이터 경계를 팀에서 정하지 않으면, 편리한 `set`을 중심으로 어디서나 서로의 상태를 수정하기 쉽다. |
| [Redux Toolkit](https://redux.js.org/toolkit/introduction/getting-started) | 여러 팀과 기능이 같은 상태를 바꾸고, 액션과 reducer로 변경 경로를 일관되게 추적하고 싶다. | 단순 화면 상태에도 같은 구조를 적용하면 변경을 이해하는 비용보다 구조를 유지하는 비용이 커진다. |
| [Jotai](https://github.com/pmndrs/jotai) | 편집기나 설정 화면처럼 작게 나뉜 상태와 그 상태에서 파생되는 값이 많다. | atom을 기능 경계 없이 만들면 하나의 사용자 행동이 어느 atom을 통해 어디까지 영향을 미치는지 찾기 어렵다. |
| [MobX](https://mobx.js.org/README.html) | observable 도메인 객체와 파생 값을 중심으로 모델을 구성하고, 읽는 값에 따라 반응성을 추적하고 싶다. | 의존성이 코드에서 값을 읽는 방식에 따라 형성되므로, 추적 범위를 팀이 이해해야 변경 원인을 좁힐 수 있다. |
| [XState](https://stately.ai/docs/xstate/v5) | 결제·업로드처럼 취소·실패·재시도에 따라 허용되는 다음 행동이 달라진다. | 모달 열림이나 선택한 탭처럼 단순한 값까지 상태 머신으로 만들면 전이 모델이 과해진다. |

Zustand와 Redux의 차이를 ‘작은 프로젝트 대 큰 프로젝트’로만 설명하면 중요한 부분을 놓친다. 화면이 많은 앱이라도 공유 상태에 쓰는 사람이 적고 변경 규칙이 단순하면 Zustand로 충분할 수 있다. 반대로 작은 앱이라도 일괄 처리, 실행 취소, 이력 추적처럼 **무슨 사건으로 상태가 바뀌었는지**가 중요하면 액션 중심 모델이 더 잘 맞는다.

XState는 또 다른 문제를 푼다. 예를 들어 배송 일괄 처리에 `isSaving`, `isFailed`, `isCanceled`, `isDone`을 모두 별도 플래그로 두면 `isSaving`과 `isDone`이 동시에 참인 상태를 표현할 수 있다. 서로 배타적이라면 우선 `idle | submitting | succeeded | failed | canceled` 같은 단일 상태로 바꿀 수 있다. 거기서 “전송 중에만 취소 가능”, “실패 후 재시도는 검증을 다시 거침” 같은 전이 규칙이 늘어날 때 상태 머신을 검토한다. **라이브러리로 옮기기 전에 불가능한 상태를 자료 구조에서 먼저 없애는 것**만으로도 문제가 많이 줄어든다.

### 공유 스토어를 쓰는데도 키 입력마다 화면이 느리다면

아래 두 구독은 같은 값을 화면에 표시할 수 있지만, 변경을 받아들이는 범위는 다르다.

```ts
// Zustand 예시: 전체 스토어를 구독한 뒤 필요한 값만 꺼낸다.
const { selectedIds } = useOrderWorkspace();

// 필요한 조각만 구독한다.
const selectedIds = useOrderWorkspace(state => state.selectedIds);
```

두 번째도 만능은 아니다. `selectedIds` 배열을 같은 내용으로 매번 새로 만들면 참조가 바뀐다. 그리고 컴포넌트가 실제로 필요한 값이 ‘선택된 개수’뿐이라면, 배열이 아니라 개수를 구독하는 편이 변경 범위를 더 정확히 표현한다.

```ts
const selectedCount = useOrderWorkspace(state => state.selectedIds.length);
```

단, 이 코드를 보고 ‘렌더가 무조건 빠르다’고 결론 내릴 수는 없다. 부모 렌더나 다른 상태에 의해서도 다시 실행될 수 있고, 파생 계산 자체가 비싸면 selector 또한 비용이 된다. 먼저 문제가 발생한 상호작용을 React Profiler로 기록하고, **관련 없는 변경이 비싼 영역까지 전파되는지** 확인한다. 그 증거가 있을 때 구독 범위를 줄이는 것이, 라이브러리 전환이나 모든 컴포넌트의 메모이제이션보다 작은 수정이다.

## 서버 데이터: 같은 주문을 세 번 저장하지 않는다

주문 상세를 수정하면 목록에도 반영되어야 한다. 문제는 목록이 하나가 아니라는 점이다.

```text
['orders', 'detail', '42']
['orders', 'list', { status: 'shipping', page: 1 }]
['orders', 'list', { status: 'delivered', page: 1 }]
```

배송 상태가 바뀌면 상세의 `status`만 바뀌는 것이 아니다. ‘배송 중’ 목록에서는 사라지고, ‘배송 완료’ 목록에는 들어갈 수 있다. 페이지 경계와 요약 건수도 달라질 수 있다. 이때 목록의 항목 하나만 찾아 상태 필드를 수정하면, 화면에는 **‘배송 중’ 필터 아래 배송 완료 주문**이 남는다.

선택지는 크게 두 가지다.

**서버 응답을 다시 읽는다.** 상세 응답이 충분하다면 상세 캐시에 그 값을 넣고, 영향받은 목록과 집계는 무효화한다. 정렬·필터·페이지 구성에 관한 판단을 서버에 맡길 수 있다. 요청이 한 번 더 생기지만, 목록의 규칙을 프론트에서 다시 구현하는 비용은 줄어든다.

**브라우저 캐시를 직접 수정한다.** 요청이 끝나기 전이라도 사용자가 변경을 즉시 봐야 한다면 유용하다. 대신 실패 시 되돌리기, 수정 중 다시 조회된 결과와 충돌하지 않기, 같은 주문을 연속으로 수정했을 때 이전 실패가 최신 성공까지 덮어쓰지 않기 등도 처리해야 한다.

실제로는 둘을 섞을 수 있다. 예를 들어 배송 메모는 수정해도 목록 소속이 변하지 않으므로 상세 화면에서만 먼저 반영할 수 있다. 반면 목록 소속이 바뀌는 배송 상태는 저장 성공 이후 목록을 재검증하는 편이 단순하다. **낙관적 업데이트는 앱 전체의 철학보다, 변경 하나의 실패 비용을 보고 정할 정책**에 가깝다.

서버 데이터 도구도 이 문제를 서로 다른 방식으로 다룬다.

| 도구 | 캐시를 다루는 방식 | 선택이 쉬워지는 상황 |
|---|---|---|
| [TanStack Query](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults) | 쿼리 키 중심으로 결과를 보관하고 최신성·재조회·수명 정책을 다룬다. | REST 등 다양한 API를 사용하고 무한 스크롤, mutation, 무효화를 명시하고 싶다. |
| [SWR](https://swr.vercel.app/) | 키로 조회 결과를 재사용하고 재검증한다. `mutate`로 갱신할 수 있다. | 조회 비중이 높고 기존 코드에서 짧은 패턴을 유지하고 싶다. |
| [RTK Query](https://redux.js.org/toolkit/rtk-query/overview) | 엔드포인트와 인자를 기준으로 캐시하고, 태그로 변경과 재조회를 연결한다. | 이미 Redux Toolkit을 사용하는 팀이 데이터 조회 규칙까지 같은 생태계에서 관리하고 싶다. |
| [Apollo Client](https://www.apollographql.com/docs/react/caching/overview) | GraphQL 결과를 엔티티 단위로 정규화해 여러 쿼리 결과에서 같은 객체를 참조할 수 있다. | 동일 엔티티가 여러 GraphQL 화면에 반복 등장한다. 다만 목록 소속·정렬·페이지 갱신은 별도 정책이 필요할 수 있다. |
| 라우터·프레임워크의 데이터 로더 | 라우트 진입과 함께 데이터를 준비하고 프레임워크가 정한 방식으로 다시 읽는다. | 데이터 수명이 화면 이동과 일치한다. 별도의 클라이언트 캐시를 추가하기 전에 내장 방식이 요구사항을 충족하는지 확인할 만하다. |

TanStack Query를 쓴다고 `staleTime`을 모든 화면에 똑같이 줄 필요는 없다. 거의 바뀌지 않는 배송사 코드와 수시로 바뀌는 미처리 주문 목록은 다른 최신성 정책을 가져도 된다. `staleTime`은 **언제 오래된 것으로 볼지**, `gcTime`은 **구독자가 없는 캐시를 얼마나 남겨둘지**를 정한다. 5분 동안 캐시를 남겨둔다고 5분 동안 데이터가 최신이라고 보는 것은 아니다. [TanStack Query의 기본 동작](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)

쿼리 키 설계도 성능 설정만큼 중요하다. 예를 들어 주문 번호가 워크스페이스 안에서만 유일하다면 상세 키에 워크스페이스도 포함해야 한다. 계정 전환 시 이전 데이터를 남겨둘지, 어떤 캐시를 제거할지도 정한다. 클라이언트 캐시 분리는 서버 권한 검사를 대신하지 않지만, 정상적으로 받아온 이전 계정 데이터가 다른 화면에 잘못 나타나는 문제는 막는 데 도움이 된다.

## 폼에는 서버의 값이 아니라 사용자의 초안을 둔다

배송 메모를 편집하는 동안 백그라운드 조회가 완료됐다고 하자. 새 응답이 올 때마다 폼을 `reset`하면, 열심히 쓰던 메모가 사라질 수 있다. 반대로 처음 읽은 값만 영원히 유지하면 다른 사람이 서버에서 수정했다는 사실을 놓친다.

이 문제에는 세 값이 있다. **편집을 시작할 때의 서버 값**, **사용자가 현재 쓰고 있는 값**, **방금 다시 조회한 서버 값**이다. 모두 ‘메모’이지만 의미가 다르다.

간단한 폼은 네이티브 `<form>`과 `FormData`, 로컬 상태로도 충분하다. 하지만 편집 화면에 배열 필드, 필드별 오류, 수정 여부, 비동기 검증이 붙으면 폼 전용 도구가 일을 줄여준다. [React Hook Form](https://react-hook-form.com/)은 `register`로 일반 입력을 연결하고 필요한 폼 상태를 구독하는 방식, [TanStack Form](https://tanstack.com/form/latest)은 타입을 활용한 필드·폼 모델을 구성하는 방식, [Formik](https://formik.org/docs/overview)은 값과 검증·제출 상태를 한곳에서 관리하는 방식을 제공한다. 기존 폼이 안정적으로 동작한다면 필드 수만 보고 마이그레이션할 이유는 없다. **복잡한 검증, 동적 필드, 외부 UI 컴포넌트 연동 중 지금 비용이 큰 곳**을 기준으로 비교한다.

주문 편집 화면이라면 다음 규칙부터 정해볼 수 있다. 주문 ID가 바뀌면 다른 폼으로 전환한다. 같은 주문에 대한 재조회라면 수정하지 않은 폼만 최신 값으로 갱신한다. 작성 중에 서버 값도 바뀌었다면 조용히 덮어쓰기보다 변경 사실을 알린다. 저장 시 덮어쓸 수 없는 업무라면 버전 확인은 서버에서도 해야 한다.

초안을 새로고침 뒤에도 살려야 할 때는 `localStorage`나 IndexedDB가 추가 선택지가 된다. 이것은 전역 상태의 대체재가 아니라 **복원 정책**이다. 사용자와 문서별 저장 키, 만료·삭제 시점, 스키마 변경, 저장해도 되는 데이터인지가 별도의 설계 대상이다. 저장소에 남겨두는 것이 곧 더 좋은 UX는 아니다. 공용 기기에서 이전 사용자의 초안이 복원되면 오히려 문제다.

## 효율을 높이려면 무엇부터 측정할까

상태 관리의 효율을 번들 크기나 렌더 횟수 하나로 판단하면 실제 손해를 찾기 어렵다. 주문 화면에서는 재현할 행동부터 정하는 편이 낫다.

| 재현할 행동 | 관찰할 것 | 먼저 바꿔볼 부분 |
|---|---|---|
| 검색어를 빠르게 입력한다 | 입력이 밀리는가, 요청이 몇 건 나가는가, 어떤 영역이 함께 렌더링되는가 | 입력 초안과 확정 조회 조건을 분리한다. |
| 상태를 저장하고 목록으로 돌아온다 | 상세·목록·건수가 같은 사실을 보여주는가 | 서버 응답을 복제한 스토어가 있는지, 어떤 목록을 무효화하는지 확인한다. |
| 메모를 쓰는 동안 재조회한다 | 입력이 사라지는가, 서버 변경을 알 수 있는가 | 저장본과 초안의 수명을 분리하고 초기화 조건을 정한다. |
| 같은 주문을 연달아 두 번 수정하고 첫 요청만 실패시킨다 | 이전 실패가 최신 수정까지 되돌리는가 | 쓰기 순서·버전 식별을 확인하고, 필요하면 낙관적 업데이트 범위를 줄인다. |
| 필터를 바꾸고 뒤로 가기·새로고침을 한다 | 검색 조건과 페이지가 기대한 대로 복원되는가 | URL을 확정 조건의 기준으로 두고 중복 저장을 없앤다. |

그리고 수치가 필요한 곳은 분리해 기록한다. 렌더를 줄이고 싶다면 같은 데이터와 동작으로 커밋 비용을 비교한다. 네트워크가 문제라면 요청 수뿐 아니라 중복 키, 응답 크기, 사용자가 실제로 기다린 시간을 본다. 저장 후 데이터가 어긋나는 문제는 빠르게 재현되는 버그일 뿐, 응답 시간이 짧다고 해결되지는 않는다.

React 밖에서도 선택 원리는 같다. Vue라면 컴포넌트의 반응형 상태에서 시작하고 여러 화면이 공유하는 상태에는 [Pinia](https://pinia.vuejs.org/)를 검토할 수 있다. Angular라면 [Signals와 `computed`](https://angular.dev/guide/signals)로 로컬 상태와 파생 값을 표현하고, 액션 중심 전역 모델이 필요하면 [NgRx](https://ngrx.io/guide/store)를 비교한다. Svelte의 [`$state`](https://svelte.dev/docs/svelte/$state)도 반응형 값을 표현하는 수단이지, URL 복원이나 서버 캐시 정책을 자동으로 정해주는 것은 아니다.

처음의 주문 화면이라면 나는 전역 스토어부터 추가하지 않겠다. **확정 필터는 URL, 조회 결과는 서버 캐시, 메모는 폼, 모달은 로컬**에 둔다. 그 뒤에도 라우트를 넘나드는 작업 목록이 필요하면 그 값만 골라 공유한다.

이미 복잡해진 코드라면 더 좋은 스토어를 찾기 전에 값 하나를 고르는 편이 빠르다. 예를 들어 `order.status`를 검색해서 서버 응답, 상세 캐시, 목록 캐시, 전역 스토어, 폼 중 어디에 같은 의미로 들어 있는지 표시해본다. 누가 값을 바꾸고, 어느 복사본이 언제 갱신되는지 설명하기 어려운 지점이 나온다. 그 복사본 하나를 없애는 일이, 상태 관리 라이브러리 전체를 바꾸는 것보다 먼저 할 만한 작업이다.
