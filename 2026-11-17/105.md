버튼을 누르면 “처리 중”을 표시하고, 데이터 가공이 끝나면 결과를 보여주는 화면이 있다. 코드에서는 분명 처리 상태를 먼저 바꿨는데, 실제로 눌러보면 잠시 멈췄다가 완료 화면만 나타난다.

중간에 `await`를 넣어봐도 비슷하다. 함수를 `async`로 바꿨으니 브라우저가 잠깐 다른 일을 할 것 같지만, 로딩 표시는 여전히 보이지 않는다.

이런 상황에서 문제는 상태를 바꾸는 코드가 실행되지 않은 것이 아닐 수 있다. **변경된 상태를 브라우저가 화면에 그릴 기회를 얻지 못한 것**일 수 있다.

`async`와 `await`는 작업을 다른 스레드로 옮기는 문법이 아니다. 그리고 JavaScript 함수의 실행이 잠깐 끊겼다는 사실만으로 입력 처리와 화면 갱신까지 가능해지는 것도 아니다. 무엇을 기다리고, 어떤 방식으로 실행을 이어가는지가 중요하다.


## 코드에서는 바뀌었는데 화면
![exec-1defa2a2-0c9c-498f-b7c4-516fa650101e.png](https://res.cloudinary.com/dcfqahfbr/image/upload/v1794918115/cvlog/posts/rireoxcfubuogow5jcap.png)
에서는 안 보이는 이유

우선 React 같은 프레임워크를 빼고 브라우저의 기본 동작만 보자.

다음 코드는 일부러 메인 스레드를 막는 실험용 예제다. 실제 서비스에서 사용하면 안 되는 바쁜 대기 루프를 넣어 문제를 드러냈다.

```html
<button id="run">처리 시작</button>
<p id="status">대기 중</p>

<script>
  const button = document.querySelector('#run');
  const status = document.querySelector('#status');

  function blockMainThread(durationMs) {
    const startedAt = performance.now();

    while (performance.now() - startedAt < durationMs) {
      // 현상을 관찰하기 위한 의도적인 동기 작업
    }
  }

  button.addEventListener('click', async () => {
    button.disabled = true;
    status.textContent = '처리 중';

    await Promise.resolve();

    blockMainThread(350);

    status.textContent = '완료';
    button.disabled = false;
  });
</script>
```

이 코드에서 `status.textContent = '처리 중'`은 실제로 DOM을 변경한다. 그렇지만 DOM을 변경하는 일과 그 결과를 픽셀로 그리는 일은 별개다.

JavaScript가 DOM에 기록한 중간 상태를 브라우저가 반드시 하나씩 화면에 보여주는 것은 아니다. 화면을 갱신하기 전에 다시 “완료”로 바뀌면, 사용자는 중간 상태를 보지 못할 수 있다.

이 예제의 `350`은 기기 성능을 비교하기 위한 측정값이 아니다. 짧은 시간 동안 의도적으로 스레드를 점유하기 위한 값이다. 여기서 관찰할 것은 정확한 소요 시간이 아니라, **DOM 변경과 화면 표시가 같은 순간에 일어나지 않는다는 사실**이다.

그렇다면 `await Promise.resolve()`는 왜 도움이 되지 않을까.

## `await` 뒤의 코드는 어디로 가는가

`await`는 현재 `async` 함수의 실행을 중단하고, 기다리는 값이 준비되면 나머지 코드를 이어서 실행하도록 한다. 이미 이행된 Promise를 기다리는 경우에도 뒷부분은 현재 함수 호출 안에서 즉시 실행되지 않고 비동기적으로 재개된다. [MDN의 await 설명](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/await)

여기까지만 보면 브라우저에 기회를 준 것처럼 느껴진다. 하지만 위 예제에서 이어지는 코드는 **마이크로태스크**로 처리된다.

마이크로태스크는 “나중에 하긴 하지만, 다음 일반 작업으로 넘어가기 전에 처리할 일”에 가깝다. Promise의 후속 처리와 `queueMicrotask()`가 이 경로를 사용한다.

브라우저는 마이크로태스크를 처리하는 동안 새 마이크로태스크가 추가되면 그것도 계속 처리한다. 큐가 비워지지 않으면 다른 작업이나 렌더링으로 넘어가는 것이 밀릴 수 있다. [MDN의 태스크와 마이크로태스크 설명](https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide)

앞의 예제로 돌아가면 흐름은 이렇다.

클릭을 처리하면서 DOM에 “처리 중”을 기록한다. `await Promise.resolve()`에서 함수 실행을 잠깐 중단한다. 하지만 그 뒤의 무거운 작업은 마이크로태스크로 이어지고, 그 작업이 끝날 때까지 메인 스레드를 다시 점유한다. 마지막에는 DOM에 “완료”를 기록한다.

함수는 중단됐다가 재개됐지만, 그 사이에 화면이 그려졌다는 보장은 없다.

그래서 아래와 같은 코드는 작업을 잘게 나눈 것처럼 보여도 응답성을 개선하는 방식이 되지 않을 수 있다.

```js
for (const item of items) {
  processItem(item);
  await Promise.resolve();
}
```

반복마다 함수의 연속 실행은 끊기지만, 다음 반복이 다시 마이크로태스크로 이어진다. 계산을 마이크로태스크의 긴 사슬로 옮겨놓았을 뿐이라면 입력과 화면 갱신은 여전히 기다려야 한다.



*블록 너비는 실행 시간을 뜻하지 않는다. 그림은 두 방식의 차이를 설명한 개념도이며, 실제 성능 기록이 아니다.*

## ‘이벤트 루프는 큐를 비우는 반복문’이라고만 외우면 놓치는 것

이벤트 루프를 설명할 때 흔히 하나의 태스크 큐를 그린다. 클릭, 타이머, 네트워크 작업이 한 줄로 들어가고 차례대로 실행되는 그림이다.

실제 브라우저의 작업 선택과 렌더링은 그보다 복잡하다. 작업의 출처가 다르고, 브라우저가 처리할 다른 일도 있다. “내 타이머를 먼저 등록했으니 다음에는 반드시 내 코드가 실행된다”거나 “태스크 하나가 끝났으니 반드시 한 프레임을 그린다”는 식으로 확대해서 이해하면 곤란하다.

프론트엔드 코드에서 실용적으로 중요한 구분은 다음 두 가지다.

하나는 현재 실행 흐름을 마이크로태스크로 계속 이어가는 것, 다른 하나는 현재 작업을 끝내고 브라우저가 다른 일을 선택할 수 있도록 양보하는 것이다.

화면이 멈추는 문제를 다룰 때 필요한 것은 보통 두 번째다.

브라우저가 사용자의 다음 입력을 처리하거나 화면을 갱신할 여지를 만드는 것. 이를 흔히 메인 스레드에 양보한다고 표현한다. 총 계산량을 줄이는 것과는 다르지만, 계산이 끝나기 전까지 사용자가 아무것도 할 수 없는 상황은 줄일 수 있다.

## `scheduler.yield()`의 Promise는 무엇이 다른가

여기서 새로운 의문이 생긴다. `scheduler.yield()`도 Promise를 반환하고 `await`로 기다리는데, 왜 `Promise.resolve()`와 다르다는 것일까.

차이는 Promise라는 자료형이 아니라 **그 Promise가 언제 이행되는가**에 있다.

`Promise.resolve()`는 이미 준비된 Promise를 만든다. 반면 `scheduler.yield()`는 작업의 후속 실행을 스케줄링해, 현재 작업을 양보하고 나중에 이어갈 수 있게 하는 API다. 브라우저가 후속 태스크를 처리해 Promise를 이행하면 `await` 뒤의 실행이 재개된다. [MDN의 scheduler.yield 설명](https://developer.mozilla.org/en-US/docs/Web/API/Scheduler/yield)

즉, `await` 문법만 보고 양보 여부를 판단할 수 없다. 기다리는 작업이 실제로 어떤 스케줄링 경계를 만드는지를 봐야 한다.

지원하지 않는 환경도 고려하면 다음처럼 작은 함수를 둘 수 있다.

```js
function yieldToMain() {
  if (typeof globalThis.scheduler?.yield === 'function') {
    return globalThis.scheduler.yield();
  }

  return new Promise(resolve => setTimeout(resolve, 0));
}
```

`setTimeout`을 사용하는 경로는 후속 코드를 타이머 태스크 이후로 이어가기 위한 대체 방식이다. `scheduler.yield()`와 우선순위 처리까지 동일한 것은 아니다. `scheduler.yield()`는 아직 모든 주요 브라우저에서 사용할 수 있는 Baseline 기능이 아니므로 지원 확인이 필요하다. [지원 상태와 기능 감지 방법](https://developer.mozilla.org/en-US/docs/Web/API/Scheduler/yield)

또한 `setTimeout(..., 0)`의 0은 정확히 0ms 뒤에 실행한다는 뜻이 아니다. 현재 작업과 대기 중인 일, 타이머 제한 등에 따라 더 늦어질 수 있다. [MDN의 setTimeout 설명](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout)

중요한 제한은 하나 더 있다. 양보했다고 해서 그 사이에 화면이 반드시 한 번 그려지는 것은 아니다. 브라우저에 다른 일을 처리할 **기회**를 주는 것이지, 모든 양보 지점에서 페인트를 명령하는 API는 아니다.

## 한 번 양보한 뒤 다시 오래 막으면 여전히 멈춘다

앞의 예제에서 한 줄을 바꾸면 어떨까.

```js
status.textContent = '처리 중';

await yieldToMain();

blockMainThread(350);

status.textContent = '완료';
```

처음부터 끝까지 쉬지 않고 실행하던 것과는 달라진다. 하지만 무거운 동기 함수가 시작된 뒤에는 여전히 오랫동안 메인 스레드를 점유한다.

로딩 문구를 표시할 기회를 만들었다고 계산 중의 화면까지 부드러워지는 것은 아니다.

여러 항목을 처리하는 작업이라면 중간에도 양보할 수 있도록 작업 자체를 나눠야 한다. 사용자 입력과 렌더링이 끼어들 수 있는 지점을 여러 번 만드는 것이다. 긴 작업을 나누는 목적도 여기에 있다. [web.dev의 긴 작업 최적화 설명](https://web.dev/articles/optimize-long-tasks)

그렇다고 항목마다 타이머를 예약하면 되느냐 하면, 그것도 지나치게 잘게 나누는 선택일 수 있다. 간단한 문자열 하나를 처리할 때마다 태스크 경계를 만들면 스케줄링 비용과 대기 시간이 커진다.

보통은 여러 항목을 하나의 묶음으로 처리한 뒤 양보한다. 문제는 묶음 크기다.

‘100개마다 양보’는 간단하지만 항목별 처리 비용이 다르면 결과가 크게 달라진다. 짧은 텍스트 100개와 복잡한 문서 100개는 같은 작업량이 아니다. 기기의 성능이 달라도 한 묶음의 실행 시간이 달라진다.

그래서 처리한 개수 대신 **이번 묶음에서 사용한 시간**을 기준으로 양보하는 방법을 고려할 수 있다.

## 시간 예산을 두고 나누는 예제

다음 함수는 동기적인 `processItem`을 실행하면서, 일정 시간 이상 작업했으면 양보한 뒤 다음 항목을 이어서 처리한다.

```js
async function processInSlices(
  items,
  processItem,
  { signal, budgetMs = 8 } = {},
) {
  if (!Number.isFinite(budgetMs) || budgetMs <= 0) {
    throw new RangeError('budgetMs must be positive and finite');
  }

  const results = [];
  let sliceStartedAt = performance.now();

  for (let index = 0; index < items.length; index++) {
    signal?.throwIfAborted();

    results.push(processItem(items[index], index));

    const hasMoreItems = index + 1 < items.length;
    const elapsed = performance.now() - sliceStartedAt;

    if (hasMoreItems && elapsed >= budgetMs) {
      await yieldToMain();
      signal?.throwIfAborted();
      sliceStartedAt = performance.now();
    }
  }

  signal?.throwIfAborted();
  return results;
}
```

여기서 `8ms`는 모든 화면에 맞는 권장값이 아니다. 예제를 위한 시작값이다. 화면 주사율, 렌더링 비용, 동시에 실행되는 다른 작업을 고려해 조정해야 한다. 8ms짜리 JavaScript만 실행하면 프레임이 항상 유지된다는 뜻도 아니다.

더 중요한 제한은 시간을 확인하는 위치다. 이 함수는 `processItem`이 **끝난 뒤** 경과 시간을 확인한다. 항목 하나를 처리하는 데 200ms가 걸리면, 시간 예산을 8ms로 설정해도 그 함수를 8ms 시점에서 끊지 못한다.

따라서 이 방식은 항목 하나하나가 충분히 작고, 작업 사이에 구분 가능한 경계가 있을 때 적합하다. 하나의 거대한 `JSON.parse`, 동기 압축 함수, 복잡한 이미지 변환처럼 내부에 접근할 수 없는 긴 호출을 이 함수로 감싼다고 잘게 쪼개지지는 않는다.

또 `processItem`은 동기 함수라는 전제다. 네트워크 요청을 병렬로 제한하거나 비동기 항목의 완료 순서를 조정하는 유틸리티는 아니다.

예제를 실제 서비스에 옮길 때는 이런 전제가 함수 이름만큼 중요하다.

## 양보하기 시작하면 취소와 오래된 결과도 생각해야 한다

하나의 긴 작업을 실행할 때는 사용자의 다음 클릭 자체가 늦게 처리된다. 일을 나누면 그 클릭을 중간에 처리할 수 있다. 이는 개선이지만, 애플리케이션이 다뤄야 할 상황도 늘어난다.

사용자가 A 조건으로 검색을 시작했다가 처리 중 B 조건으로 바꿨다고 해보자. 이제 A 계산이 끝나기 전에 B 계산이 시작될 수 있다. A가 나중에 끝나 현재 결과를 덮어쓰면 화면은 다시 잘못된다.

앞의 함수에 `signal`을 둔 이유다. 새 작업을 시작할 때 이전 작업을 취소하고, 취소된 작업의 결과를 반영하지 않는 구조를 만들 수 있다.

다만 이 취소도 즉각적인 강제 중단은 아니다. 코드가 취소 상태를 확인하는 지점에 도달해야 멈춘다. 실행 중인 `processItem` 하나를 바깥에서 끊는 것은 아니다.

처리 도중 원본 배열을 바꿔도 괜찮은지 역시 정해야 한다. 사용자의 다른 동작이 같은 배열에 항목을 추가하거나 순서를 바꾸면, 분할 처리 중 읽는 데이터가 달라질 수 있다. 필요하다면 작업 시작 시 입력의 스냅샷을 만들거나, 작업 동안 해당 데이터를 변경하지 않는 계약을 둬야 한다.

동기 코드를 비동기 흐름으로 바꾸는 것은 단순한 성능 수정이 아니다. **작업 도중 세상이 달라질 수 있도록 허용하는 변경**이기도 하다.

## `requestAnimationFrame`으로 감싸면 해결되지 않을까

화면 갱신과 관련된 API라는 이유로 다음처럼 바꾸는 경우도 있다.

```js
requestAnimationFrame(() => {
  blockMainThread(350);
});
```

하지만 `requestAnimationFrame` 콜백은 다음 화면을 그리기 **전에** 호출된다. 그 안에서 무거운 계산을 실행하면 화면을 그리기 직전의 중요한 구간을 다시 막을 수 있다. [MDN의 requestAnimationFrame 설명](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

이 API는 애니메이션에 필요한 시각적 변경을 프레임과 맞추는 데 유용하다. 대량의 CPU 작업을 넣어두면 브라우저가 알아서 화면을 먼저 보여주는 대피소가 아니다.

비슷하게 `Promise.all`도 CPU 계산을 다른 스레드에서 병렬 실행하는 도구가 아니다.

```js
await Promise.all(
  rows.map(async row => expensiveTransform(row)),
);
```

`expensiveTransform`이 동기 계산이라면 위 코드도 같은 스레드에서 그 함수를 호출한다. `async`로 감싼 함수와 Promise 배열을 얻을 뿐, CPU 코어에 일을 나눠주지는 않는다.

문법상 비동기와 실제 실행 자원의 분리를 구분해야 하는 이유다.

## 계산을 나눌 것인가, 메인 스레드 밖으로 옮길 것인가

분할 처리는 계산을 메인 스레드에서 계속하되 독점 시간을 줄이는 접근이다. 계산량 자체는 남는다. 양보를 위한 비용 때문에 전체 완료 시간은 늘어날 수도 있다.

반면 Web Worker는 별도의 작업 스레드에서 계산을 수행하는 방법이다. DOM을 직접 다룰 수 없고 메시지로 데이터를 주고받아야 하므로, 메인 스레드의 함수를 그대로 옮기는 것과는 다르다. [MDN의 Web Worker 사용 안내](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)

판단할 때는 작업의 경계를 보면 된다.

브라우저 DOM을 자주 읽고 수정해야 하는 작업인지, 순수한 데이터 계산인지. 입력 데이터가 얼마나 큰지, 전달 비용이 얼마나 드는지. 작업 한 번이 긴지, 작은 계산이 많이 쌓인 것인지.

예를 들어 DOM과 관계없는 대규모 문서 분석이라면 Worker를 검토할 이유가 있다. 반대로 이미 작은 단위로 구분된 UI 관련 작업이라면 메인 스레드에서 나누는 편이 단순할 수 있다.

그 전에 아예 계산을 덜 할 수 있는지도 봐야 한다. 사용자가 검색어를 한 글자 입력할 때마다 동일한 원본 전체를 여러 번 순회하고 있다면, 스케줄링을 바꾸기 전에 중복 계산을 줄이는 쪽이 더 큰 개선일 수 있다.

## 완료 시간과 응답성은 따로 기록한다

작업을 나눈 뒤 전체 처리 시간이 조금 늘었다면 실패한 최적화일까.

그동안 버튼이 눌리지 않던 화면에서 사용자가 입력하고 작업을 취소할 수 있게 됐다면, 분명 얻은 것이 있다. 반대로 전체 처리 시간만 줄었는데 그동안 화면이 계속 멈춰 있었다면 응답성 문제는 남는다.

검증할 때도 두 질문을 나눠야 한다.

첫 번째는 결과가 준비되기까지 얼마나 걸렸는가다. 두 번째는 그동안 사용자가 무엇을 할 수 있었는가다.

브라우저 성능 기록에서는 JavaScript가 길게 실행되는 구간과 그 사이의 입력·렌더링 작업을 함께 본다. 로딩 문구가 잠깐 보였다는 사실만으로 계산 중의 응답성까지 해결됐다고 판단하지 않는다. 테스트 데이터 크기, CPU 조건, 브라우저 버전도 남겨야 비교가 된다.

특히 데스크톱의 빠른 기기에서 잘 동작한다고 모바일에서도 같은 크기의 작업 묶음이 적절하다고 볼 수는 없다.

프론트엔드에서 `await`가 중요한 이유는 기다림을 코드로 표현할 수 있기 때문이다. 하지만 기다리는 코드를 썼다는 사실만으로 사용자의 기다림까지 줄어드는 것은 아니다.

화면이 멈춘다면 “비동기로 바꿨는가”보다 먼저 물어볼 질문이 있다.

**지금 이 코드는 메인 스레드를 얼마나 오래 놓아주지 않는가. 그리고 놓아준 뒤 다른 일을 처리할 기회가 실제로 생기는가.**

이 질문에 답할 수 있으면 Promise를 하나 더 감싸는 대신, 작업을 줄일지, 나눌지, 다른 스레드로 옮길지 선택할 수 있다.

*브라우저 메인 스레드를 기준으로 설명했다. 실행 순서 그림은 개념도이며, 특정 기기에서 측정한 성능 결과가 아니다. `scheduler.yield()`의 지원 상태는 2026년 11월 16일 기준 공식 문서를 확인했다.*
