Before you compare Meta’s new models with your current coding assistant, check which one you can actually use.

**Muse Wonder is available through the Meta Model API. Muse Wonder Full is exclusive to selected Muse Code subscriptions at launch.** These are different access routes, not interchangeable ways to buy the same model. Meta’s October 12 developer announcement makes that distinction explicit. [Source: Meta’s developer announcement](https://dev.meta.ai/resources/blog/build-with-muse-wonder)

That matters more than a leaderboard screenshot if you are deciding what to put inside your own product.

## The price you can put in a spreadsheet

Meta lists the following for Muse Wonder. Token prices are in USD per million tokens; the context figures are listed capacities, not a promise that every task should fill the window.

| Item | Muse Wonder | Muse Wonder Full |
| --- | --- | --- |
| Input tokens | $4 | No general API token rate listed on the model page |
| Cached input tokens | $0.20 | Not listed as a token-priced API offering |
| Output tokens | $20 | Not listed as a token-priced API offering |
| Context | 1 million tokens | 1 million tokens |
| Access | Meta Model API and Muse Code | Muse Code Power Usage and Maximum Usage plans |

Sources: [Meta’s model page](https://dev.meta.ai/models/muse-wonder) and [developer launch details](https://dev.meta.ai/resources/blog/build-with-muse-wonder), checked October 13, 2026.

Here is a deliberately simple estimate. Suppose your application records 100,000 uncached input tokens and 10,000 output tokens for a task. At the listed rates, those tokens cost:

`(100,000 / 1,000,000 × $4) + (10,000 / 1,000,000 × $20) = $0.60`

This is an illustrative token calculation, not a measured task or an all-in bill. It excludes other applicable charges and assumes those are the billable quantities. Extra attempts increase usage; actual cache eligibility changes the input calculation.

The useful question is not whether sixty cents sounds cheap. It is how much verified work those tokens buy.

## A coding subscription is not your application's API budget

Picture two developers interested in the same launch.

One wants help refactoring a repository inside a coding tool. The other wants a model behind a customer-facing service, with their own tools, request handling and billing controls.

The first can evaluate whether a Muse Code plan fits their workflow. The second needs to evaluate the API-accessible model. A subscription offering Full does not, by itself, establish that Full can be called from their application.

This sounds obvious until a comparison mixes a stronger subscription-only model’s results with another model’s API price. The resulting bargain may not be something anyone can actually purchase.

Keep three labels beside any result you use: the exact model, the reasoning setting, and the environment in which it ran. If one is missing, the comparison is incomplete for a buying decision.

## What Active Memory should mean in your own test

Meta describes Active Memory as retaining important context across conversations and retrieving relevant details. Active Focus concerns sustained progress: trying alternative approaches, adapting to new information and checking in when necessary. Those are the company’s capability descriptions, not findings from hands-on testing for this article. [Source: Meta AI Research](https://research.meta.ai/blog/muse-wonder)

For a useful evaluation, give the agent something more revealing than a large prompt: a changed decision.

Start a small project with a clear constraint. In a later interaction, replace that constraint and explain why. Then ask for the next piece of work. Does the agent apply the new decision, revive the old one, or repeatedly ask you to explain the change?

This is a proposed test, not a reported Muse result. It probes the difference between remembering information and keeping the right information current.

Also separate the model from the surrounding application. A claim about memory is not a complete specification of how your integration stores state, isolates users or deletes old information. Verify those behaviors in the interface and documentation you intend to use.

For an API project, begin with the model and costs you can actually access. For a coding-tool subscription, evaluate the complete working experience under its usage limits. Do not let a shared family name turn those two decisions into one.
